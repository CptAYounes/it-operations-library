# Linux firewall fundamentals

A Linux host may be filtered by nftables directly, a frontend such as UFW/firewalld, legacy iptables compatibility rules, container orchestration, and upstream controls at the same time. Identify the active owner before changing any rule.

> **Remote-access boundary:** an input-policy or SSH-rule error can cut off the current and all future sessions. Keep console/out-of-band access, preserve the current ruleset, add and test the required management path before tightening defaults, and arrange automatic rollback where the platform supports it.

## The packet path

The main host decisions are:

- **input** — traffic addressed to this host;
- **output** — traffic generated by this host;
- **forward** — traffic routed through this host, including some container/VM paths;
- **NAT** — address/port translation, separate from whether filtering allows the packet;
- **connection tracking** — state such as `new`, `established`, `related` and `invalid` used by stateful rules.

A service is exposed only when all layers align: it listens on an address, local policy accepts the traffic, upstream policy and routing permit it, and the application completes its protocol. A firewall “allow” does not create a listener.

## Discover the active stack

Package and service names vary. Use whichever tools exist, without installing or enabling a second manager during an incident.

```bash
systemctl status nftables.service --no-pager
systemctl status ufw.service --no-pager
systemctl status firewalld.service --no-pager
```

Privileged read-only views:

```bash
sudo nft list ruleset
sudo iptables-save
sudo ip6tables-save
sudo ufw status verbose
sudo firewall-cmd --state
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --list-all-zones
```

Not every command will exist. `iptables` output may be a compatibility view backed by nftables. UFW and firewalld generate lower-level rules; editing both the frontend and its generated tables makes ownership unclear.

Also inspect listeners and addresses:

```bash
ss -lntup
ip -brief address
ip route
```

Record the actual interface, address family, source network, protocol and destination port required. “Open port 443” is incomplete if the service should be limited to one interface or management subnet.

## Read rules in evaluation order

For each relevant hook/chain, identify:

1. table and address family (`ip`, `ip6`, `inet`, bridge or other);
2. hook and priority;
3. default policy;
4. early accepts/drops/jumps;
5. interface, source/destination, protocol and port matches;
6. connection-state handling;
7. counters/logs;
8. user-defined chain return path.

A later allow cannot override an earlier terminal drop in the same path. Conversely, an early broad accept can make later restrictions irrelevant. Packet counters prove a rule matched something, not that it matched the intended flow or that the application responded.

Linux firewalls must handle IPv6 deliberately. Disabling or ignoring it while interfaces retain IPv6 can create a different exposure than IPv4. ICMPv6 is required for core IPv6 operation such as neighbour discovery and path MTU; a blanket ICMPv6 drop breaks networking.

## nftables model

Modern Debian supports nftables, but the `nft` userspace package and persistent service may not be installed on every host. An `inet` table can handle IPv4 and IPv6 in one ruleset. Base chains attach to hooks; ordinary chains are reached by jump/goto.

This is a **teaching fragment**, not a production-ready ruleset and not a command to paste into a remote host:

```nftables
table inet filter_example {
    chain input {
        type filter hook input priority filter; policy drop;

        iifname "lo" accept
        ct state invalid drop
        ct state established,related accept
        ip protocol icmp accept
        meta l4proto ipv6-icmp accept
        ip saddr 192.0.2.0/24 tcp dport 22 accept
    }

    chain forward {
        type filter hook forward priority filter; policy drop;
    }

    chain output {
        type filter hook output priority filter; policy accept;
    }
}
```

The source is an RFC documentation network. A real host may also need DHCP, routing protocols, monitoring, clustered traffic, VPN, container forwarding or IPv6 management. The example's default-drop policy would block anything not explicitly allowed.

Validate a proposed nftables file syntactically, with the installed version and appropriate privilege, before applying it:

```bash
sudo nft --check --file /path/to/proposed.nft
```

A syntax pass does not prove reachability, correct chain priority, interaction with generated rules or persistence. Applying a complete ruleset may replace working state and disrupt containers/VMs. Review the exact transaction and rollback separately.

## Frontends

### UFW (common on Ubuntu, optional elsewhere)

```bash
sudo ufw status numbered
sudo ufw status verbose
```

UFW commands such as `allow`, `delete`, `default` and `enable` change policy. Check both IPv4/IPv6 handling, routed policy, application profiles and generated rules. Enabling UFW on a remotely managed host without a tested SSH allowance can lock it out.

### firewalld (common on Fedora/RHEL)

```bash
sudo firewall-cmd --get-active-zones
sudo firewall-cmd --get-zone-of-interface=interface-name
sudo firewall-cmd --zone=zone-name --list-all
sudo firewall-cmd --get-services
```

firewalld distinguishes runtime and permanent configuration. A runtime change can disappear at reload/reboot; a permanent change may not affect runtime until reloaded. Record and validate both rather than assuming `--permanent` means active.

### iptables compatibility

```bash
sudo iptables -S
sudo iptables -L -n -v
sudo ip6tables -S
```

Check whether `iptables -V` reports an nf_tables backend. Persistence depends on distribution tooling. Do not mix `iptables-nft`, `iptables-legacy`, raw nftables and a frontend without an explicit design.

## Safe change plan

Before an approved rule change:

- [ ] State the exact required flow: source, destination/interface, IP family, protocol and port.
- [ ] Confirm a listener exists or is planned and bind scope is correct.
- [ ] Capture rules, counters, frontend state and upstream dependencies.
- [ ] Identify the canonical configuration and how it persists after reboot.
- [ ] Keep an independent console and known-good session.
- [ ] Arrange a timed/automatic rollback if the management platform supports one.
- [ ] Add the narrow required allow before removing a broad one or changing default policy.
- [ ] Validate from an authorised client in the intended source network.
- [ ] Test an unauthorised source/path where safe to prove the boundary.
- [ ] Remove temporary rules and validate a reload/reboot under change control.

Do not flush an entire ruleset to troubleshoot one port. It removes evidence, can expose unrelated services and may break NAT or container networking.

## Diagnose a blocked flow

1. Confirm name resolution and route on the client.
2. Confirm the service listens on the intended server address and port.
3. Test TCP/UDP with an application-aware probe where possible.
4. Inspect host rule order, address family, interface/zone and counters.
5. Check upstream firewall, security group, load balancer and return route.
6. Compare a known-good source or destination.
7. Use a tightly filtered packet capture only with authority and secure handling.

Typical distinctions:

- **refused** often means an active reject or no listener;
- **timeout** can mean filter/drop, route failure, asymmetric return, overload or silent application behaviour;
- **locally works, remotely fails** points toward bind scope, host/upstream filtering or path—not automatically the host firewall;
- **counter never moves** can mean wrong chain/hook/family/interface, or traffic never reached the host.

Container engines and Kubernetes can create rules, bridges and NAT paths dynamically. Docker-published ports may interact with host policy in ways a simple input-chain inspection misses. Use the platform's supported integration point and do not delete generated chains during live operation.

## Logging without creating another incident

Firewall logging should be narrow and rate-limited. Broad logging of denied Internet traffic can fill storage, consume CPU and collect addresses or payload-adjacent metadata. Use counters first, enable a scoped log rule for a bounded window, then remove it and handle evidence as sensitive operational data.

## Validation and escalation

A firewall change passes when the intended flow succeeds end to end, unintended scope remains denied, active rules match the saved configuration, counters/logs support the expected path, containers/VPN/routing still work, and the policy survives the approved reload or reboot.

Escalate for loss of management access, unclear ownership between tools, default-policy or forwarding/NAT changes, cluster/container networking, suspected attack traffic, IPv6 uncertainty, or any rule outside the authorised host scope. Provide the five-tuple, direction, interface/zone, timestamps, rule/counter evidence and upstream checks—redacted where necessary.
